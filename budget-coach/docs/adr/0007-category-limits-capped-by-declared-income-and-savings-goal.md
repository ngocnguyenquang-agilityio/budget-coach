# Category Limits are capped by Declared Income minus Savings Goal

Category Limits were previously computed purely from trailing spend (`spend * 1.1` per Category, via `proposeCategoryLimits`), with no relationship to Income or Savings Goal at all — a Category Limit could exceed what the user actually earns. We introduced **Declared Income**, a new explicit and persisted figure (same working-memory pattern as Savings Goal) distinct from `Income` (the Transaction type), because actual Income for the current Period isn't known until the Period ends and Category Limits need to be forward-looking. Declared Income is never inferred from summed Income Transactions — it's collected via a frontend `useHumanInTheLoop` box when a Monthly Review is triggered (Cancel aborts before the workflow starts, so nothing needs discarding), and can later be updated conversationally when the user states a new figure directly, or when the Coach notices the Period's actual Income Transactions have drifted more than 20% from the stored value. Per-Category proportions still come from trailing spend as before; the total is now scaled down (never up) to fit within `Declared Income − Savings Goal` when it would otherwise exceed that cap. If the cap would be negative or unworkable (Savings Goal exceeds Declared Income), the Monthly Review refuses to propose limits and flags it rather than producing degenerate near-zero limits.

## Considered Options

- **Derive Income from trailing/actual transactions instead of declaring it explicitly** — rejected because it would lag behind real changes (a raise, job loss) by a full Period, and Category Limits are meant to be forward-looking allowances, not backward-looking reports.
- **Scale Category Limits up to fully use the cap when trailing spend leaves room to spare** — rejected because it would invent spending room not grounded in actual habits; unused headroom below the cap is not a limits problem, it just shows up as extra Net Savings.
- **Detect income changes only by comparing actual transactions against Declared Income (no conversational path)** — rejected in favor of trusting the user's direct statement too, consistent with the explicit-only pattern already established for Coach Preferences (ADR-0006).

## Consequences

Working memory (`BudgetStateSchema`) gains a `declaredIncome` field, persisted the same way `savingsGoal` and `categoryLimits` are. The Monthly Review workflow gains a pre-workflow income-collection step (frontend HITL, not a new server-side suspend/interrupt) and now requires a Savings Goal to already be set before it can run. A new proactive Coach behavior monitors Income Transactions for >20% drift from Declared Income and offers an out-of-cycle Monthly Review; declining still updates the stored Declared Income immediately (the statement is trusted) but leaves Category Limits untouched until an actual review is approved, and suppresses re-offering for the rest of that Period.
