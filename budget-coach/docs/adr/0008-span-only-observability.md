# Observability is span-only; metrics are out of scope

The project's observability was scoped to four signals — traces, logs, metrics, and error visibility — with a hard constraint of **no new infrastructure** (no Docker containers, no hosted SaaS, no API keys). Investigating the installed packages against that constraint collapsed the scope to what LibSQL can physically store: **spans**.

Two findings drove this. First, **metrics require an OLAP store.** `@mastra/core`'s own bundled documentation (`docs-studio-observability.md`) states: *"Metrics require a separate OLAP store for observability. Relational databases like PostgreSQL, LibSQL, etc. aren't supported for metrics."* Locally that means DuckDB — which this project rejected three separate times (`docs/implementation-plan.md`, `docs/spec.md`, `docs/tickets/02-mastra-infrastructure.md`) over Windows file-lock complexity. Second, and less obviously, **logs don't persist either.** `ObservabilityLibSQL` implements `createSpan`/`getTrace`/`listTraces` and nothing else — its own comment reads *"Spans are the only physical table."* The base class defines `batchCreateLogs`/`listLogs` as defaults that throw "not implemented", and `MastraStorageExporter` responds by disabling the signal for future flushes. The `logging: { enabled: true, level: "info" }` block in `src/mastra/config/observability.ts` is therefore inert: Studio's Logs tab has no backing table, and log lines reach the terminal only.

So spans carry every countable event. Each one is tagged with a filterable `metadata.event` value (`src/constants/observability.ts`), because span `tags` are valid on root spans only, and Studio can render a top-level metadata key as a sortable column. A tool failure marks its span errored via `span.error()` — without that, `withToolErrorHandling`'s deliberate conversion of throws into `{ success: false }` makes a failed tool indistinguishable from a successful one in the trace. A guardrail block emits an event span (`createEventSpan`, no `endTime`) because a block is an instant, not an interval.

## Considered Options

- **Add `@mastra/duckdb` as the `observability` domain of a `MastraCompositeStore`** — rejected. It would have bought the full Studio Metrics dashboard, latency percentiles, token counts, and bundled model-cost estimation, and a composite store would have confined DuckDB to the observability domain so a file lock degraded dashboards rather than corrupting a Monthly Review's suspend/resume. Rejected anyway to keep the original no-DuckDB decision intact on Windows, at the cost of the metrics pillar.
- **OpenTelemetry Collector + Jaeger in Docker** — rejected by the no-new-infrastructure constraint. It would have taught the vendor-neutral standard and kept financial data local, but this is a learning project running on one Windows machine, not a deployment.
- **Hosted SaaS (Sentry, Langfuse, Braintrust, Axiom)** — rejected for the same constraint, and because these traces carry transaction data and Clerk user ids that would leave the machine.
- **A hand-rolled `observability_events` table in LibSQL** — rejected as duplicating `listTraces` while requiring its own retention, query layer, and UI.
- **Emit `metrics.emit(...)` calls that no-op until a store exists** — rejected: instrumentation that can't be read is indistinguishable from broken instrumentation.

## Consequences

"How often did X happen" is answered by walking spans, not by querying metrics. `listTraces` filters on `status`, `hasChildError`, `spanType`, `metadata`, `entityName`, and a `startedAt` range, and returns `pagination.total` — but it returns **root spans only**, and LibSQL exposes no `getSpans`. Counting child-span events therefore requires fetching each trace individually (`getTrace`) and walking its spans, which is what `scripts/observability-report.ts` (`pnpm report:observability [days]`) does. That N+1 pattern is acceptable against a local dev database and would not be against a remote Turso one.

Latency has no percentile store, so the report script computes p50/p95 itself from each span's `startedAt`/`endedAt`. There is no cost or token tracking of any kind — the pricing data ships inside `@mastra/observability` but is only reachable through the metrics path.

The inert `logging` block stays in `src/mastra/config/observability.ts` with a comment, so the config starts working unchanged if the store ever gains an OLAP backend. Structured logs still go through `observe.log` inside tools rather than `console.*`, which keeps them trace-correlated for the day they do persist and gives a readable terminal line today. `src/lib/with-error-handling.ts` and `src/middleware.ts` remain console-only: route handlers and Clerk edge middleware run outside Mastra entirely, and middleware cannot import the Mastra instance. They emit the same `{ event, ... }` JSON shape for consistency, not for searchability.

`src/mastra/guardrails/block-channel.ts` gains an optional `span` parameter rather than importing anything from `@/mastra`, preserving the leaf-module invariant that keeps guardrail processors free of a circular import back through the Mastra instance.
